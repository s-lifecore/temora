# DB／バックエンドに Convex を選んだ理由

2026-11-20 決定。v1 は Supabase で作り、2026-11-21 に Convex へ移行した。

## このアプリがバックエンドに求めること

1. **状態遷移を二重に実行しない**：案の受付 → AI 照合 → 承認 → 決定、を複数人が同時にアクセスしても1回だけ進める
2. **締切で勝手に進む**：誰も画面を開いていなくても、締切の時刻に次の段階へ進む（元祖 MeetForMe は代表者の画面が開いている間しか進まなかった）
3. **全員の画面にすぐ反映する**：誰かが提出・承認したら、ほかの人の画面も変わる

## Supabase 版（v1）での実現方法と不満

| 要件           | v1 の実装                                                                                        | 不満                                                               |
| -------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 二重実行の防止 | `update ... where phase = X and round = N` の条件付き更新、AI 処理は `lock_until` 列で自前ロック | ロックの期限切れや失敗時の戻しを自分で管理している                 |
| 締切で進む     | 誰かが API にアクセスしたときに締切を判定して進める（遅延評価）                                  | 誰もアクセスしなければ進まない。本当の意味で「勝手に進む」ではない |
| 画面への反映   | 3秒ごとの問い合わせ（ポーリング）                                                                | 無駄なリクエストが多く、反映も最大3秒遅れる                        |

## Convex なら

| 要件           | Convex での実現                                                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 二重実行の防止 | mutation がトランザクションとして直列に実行されるので、自前ロックが要らない                                                               |
| 締切で進む     | scheduler（`runAt`）で締切の時刻に関数を予約できる。アクセスがなくても進む                                                                |
| 画面への反映   | クエリがリアクティブなので、データが変わると購読中の画面に自動で届く。ポーリング不要                                                      |
| AI 呼び出し    | action（外部 API を呼べる関数）から Claude を呼び、結果を mutation で書き込む。サーバー側で固定モデル・同じ指示という方針はそのまま守れる |

自前で書いていた仕組み（遅延評価・ロック・ポーリング）がほぼ消え、ルール（`src/lib/rules.ts`）と AI 呼び出し（`src/lib/ai.ts`）だけが残る形になる。

## ほかの候補と比べて

| 候補                                  | 見送った理由                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Supabase のまま（Realtime + pg_cron） | 同じことはできるが、締切ごとのジョブ登録やリアルタイム購読を別々に組む必要があり、自前の部分が残る                              |
| Neon / Turso                          | DB だけなので、締切とリアルタイムは別途用意が必要                                                                               |
| Cloudflare Durable Objects            | 「会議1つ＝オブジェクト1つ」で設計はきれいだが、Workers 前提になり学習コストが最も高い                                          |
| Firebase（Firestore）                 | リアルタイムと匿名ログインは手軽だが、表どうしのつながりが多いデータには窮屈。締切には Cloud Functions のスケジュール実行が要る |

## 受け入れたトレードオフ

- SQL ではなく Convex 独自の書き方になる。ほかのサービスに乗り換えにくい
- ローカルでの開発は Convex の dev デプロイを使う（Supabase のように Docker で丸ごと手元に立てる形ではない）
- 無料枠や料金は変わりうるので、公開前に最新を確認する
